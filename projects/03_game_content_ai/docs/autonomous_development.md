## 4. 基本フロー
```
[統括] WP記録の作成直前に、作業ツリーがクリーンであることを確認（6.3節）
[統括] WP記録をDRAFTで作成し、実行計画（plan-before-code の3行宣言）・許可ファイル・許可された副産物・検証コマンドと期待結果・完了条件を確定（6.2節）
[人間] 確定したDRAFTを承認（DRAFT → APPROVED）
[統括] 開始時の状態を記録（6.3節。チェックポイント0）→ IN_PROGRESS
[実装] 許可ファイルを作成・編集
[検証] 検証コマンドを実行・報告
[統括] FAIL なら修正を依頼（実装→検証は最大3サイクル）
[統括] （WP記録5.1節でCodexの使用が承認されている場合のみ）Codex独立レビュー（14章）
[統括] 完了条件を満たしたら READY_FOR_GATE で停止
[人間] 保持（commit等は別Gate）または破棄を判断 → CLOSED
```

## 5. 停止条件
次のいずれかに該当したら、統括はWPの状態を `STOPPED` にし、停止記録を書いて人間に報告する。

| ID | 条件 |
|---|---|
| S1 | Human GateのBlock、または権限拒否が1回でも発生した。同じ操作の再試行、言い換え、別のツール・シェルでの代替実行、別のサブエージェントへの再委譲はしない |
| S2 | 許可ファイル（WP記録自身を含む）と許可された副産物（6.5節）以外の差分が発生した |
| S3 | HEADや作業ツリーの状態が、開始時は開始時の記録と、再開時は直近の完了済みチェックポイント（6.4節）と一致しない |
| S4 | canonical leafの集約値（ファイル数・集約ハッシュ）が、開始時の記録または直近の完了済みチェックポイントと一致しない（6.6節の対象WP（WP-P1・WP-P2）は判定しない） |
| S5 | 同じ原因のテスト失敗を2回修正できなかった（`debug-root-cause` の2回ルール）、または実装→検証が3サイクルを超えた |
| S6 | 要件が曖昧、または設計変更・依存追加・外部I/O・ネットワークが必要になった。承認済みの記載の重要変更（6.2節）が必要になった場合を含む（再承認まで停止） |
| S7 | commit / push / tag / deploy が必要になった（`READY_FOR_GATE` で止める）。または、14章の条件を満たさないCodex起動（承認された回数を超える再実行を含む）が必要になった |
| S8 | サブエージェントが `STOP` を返した、または想定外の事象を報告した。Codex wrapperの異常（14.4節のC-WRAPPER）、期待結果に終了コードを含む検証で終了コードが未取得の場合（6.7節）を含む |
| S9 | Codexレビューの判定が `NOT APPROVED` だった（14.4節のC-NOT-APPROVED）。自動修正はしない |

## 6. WP記録と進捗
### 6.1 置き場所
`projects/03_game_content_ai/docs/work_packages/WP-<ID>.md`。ひな形は `docs/templates/work_package_template.md`。WP記録自身は、そのWPの許可ファイルに必ず含める。

### 6.2 状態
`DRAFT → APPROVED → IN_PROGRESS → READY_FOR_GATE または STOPPED → CLOSED（KEPT / DISCARDED）`
- `DRAFT → APPROVED` は人間の承認でのみ遷移する（承認の文言と日時を記録する）。
- 統括は、実行計画（3行宣言・完了条件）、許可ファイル、許可された副産物、検証コマンドと期待結果、上限を**DRAFTの段階で確定**させてから、人間に承認を求める。未確定の項目を残したまま承認を求めない。
- 承認後に統括が更新してよいのは、状態、承認欄（0章の「承認」「Codex起動の承認」。人間の承認の転記に限る）、開始時の記録、進捗ログ・チェックポイント、停止記録、終了欄だけ。それ以外の記載の変更（許可ファイル・副産物・検証コマンド・期待結果・完了条件・上限の追加・変更・削除）は**重要変更**とし、統括は作業を止め（S6）、変更案を停止記録に書いて人間の再承認を待つ。再承認の文言と日時は再開・再承認記録に残す。
- **自己承認の禁止**：承認欄と再開・再承認記録には、人間が実際に示した承認・判断の文言の要旨と日時だけを転記する。統括は自らの判断で「承認」「承認済み」と記録しない。人間の承認が会話等で確認できない場合は「未承認」のままとする。
- `STOPPED → IN_PROGRESS` は人間の再開判断（重要変更の場合は再承認）が記録された場合にのみ遷移する。

### 6.3 開始時の記録
- **前提**：Phase Aの成果物がGitに登録済みであること（10章・11章）。WP記録の作成直前に、作業ツリーがクリーン（未追跡・未commitの差分がない）であることを確認する。満たさなければWP記録を作成しない（S3）。
- WP記録の作成後は、WP記録自身の差分だけを許容する。開始時の作業ツリーは「WP記録自身以外の差分がない」ことを確認する。
- HEAD、ブランチ、作業ツリーの状態（確認方法は12章の確認事項。Phase Bの承認前に確定する）
- canonical leafのファイル数と集約ハッシュ（読み取りのみ。6.6節の対象WPは「N/A（6.6節の例外）」。WP-P1の記録では「N/A（WP-P1限定）」）
- 起動方法（通常起動・auto mode不使用）
- 開始時の記録を**チェックポイント0**とする。

### 6.4 進捗ログとチェックポイント
- 各段階の終了ごとに、統括が1行追記する。過去の行は書き換えない（追記のみ）。
- 記録する項目：日時、段階、担当、結果、証拠（コマンド、終了コード、出力の要点）。
- 段階が完了したら、統括はチェックポイントを追記する：HEAD、作業ツリーの変更ファイル一覧（WP記録自身を含む）、WP記録自身を除く各変更ファイルのSHA-256、canonical leafの集約値（6.6節の対象WPは「N/A（6.6節の例外）」）。段階の途中ではチェックポイントを書かない（取得方法は12章で確定する）。
- WP記録自身はチェックポイントを書くたびに変わるため、SHA-256の対象にしない。代わりに次の2点を別途確認する。一致しなければS3で停止する。
  1. 承認済みの固定項目（1〜5章）が、承認時（再承認があれば最新の再承認時）の内容から変わっていない。
  2. 進捗ログとチェックポイントが追記だけで書かれており、最新のチェックポイントが直近に完了した段階と一致する。

### 6.5 許可された副産物
- 検証コマンドの実行に伴って生じる書き込み（例：テストが `tempfile` で作る一時ファイル・一時ディレクトリ、Pythonが生成する `__pycache__/`）は、WP記録の「許可された副産物」に、場所・生じる原因（検証コマンド番号）・後片付けを事前に列挙した場合に限り許可する。
- 列挙されていない書き込みは、検証担当の禁止事項であり、停止条件S2の対象とする。

### 6.6 WP-P1・WP-P2限定の例外（canonical leafの集約値確認）
- 人間の承認（WP-P1：2026-11-24。WP-P2への拡大：2026-11-24、Phase C2の最終修正）による限定的な改訂。**対象はWP-P1とWP-P2だけ**であり、他のWP、正式Release（Release 6.38を含む）、L3-D2、その他の正式開発には適用・拡大しない。
- 理由：WP-P1・WP-P2は、Release 6.38・L3-D2から独立したパイロットであり、canonical leafに関わらないため。また、canonical leafの集約値を取得する読み取り専用コマンドが未確定のため（12章）。
- 対象WPでは、canonical leafを読み書きしない（集約値を取得するための読み取りも行わない）。作業中にcanonical leafへのアクセスが必要になった場合は、S6として停止する。WP-P2では、Codexに渡す範囲文（5.1節の対象）にもcanonical leafを含めない。
- 対象WPの開始時の記録（6.3節）、チェックポイント（6.4節）、復旧時の照合（7章）、終了欄では、canonical leafの欄を「N/A（6.6節の例外）」と記録する（WP-P1の記録では「N/A（WP-P1限定）」）。PASS・一致とは記録しない。停止条件S4は、対象WPでは判定しない。
- 次の確認は、対象WPでも維持する：許可ファイルと許可された副産物（S2）、HEAD・作業ツリー・WP記録自身を除く各変更ファイルのSHA-256（S3）、WP記録の整合性（6.4節の2点）。
- Human Gate、既存Hooks、権限設定、S4以外の停止条件（S1〜S3、S5〜S9）の適用は変えない。
- **WP-P2の残存リスク**：WP-P2では、統括・サブエージェントとは別のプロセスとしてCodexが起動する（14章）。wrapperは `--write` を構成・受理しないと記載されているが、Codexが実際に読み取り専用で動作し、canonical leafに書き込まないことは未検証である（13章）。本例外の下ではcanonical leafの集約値を取得しないため、Codexによるcanonical leafへの影響は検出できず、完全には否定できない。WP-P2の終了欄（10章）と最終報告には、この点を明記する。

### 6.7 実測証拠の記録（Phase C2で追加）
- 対象：WP記録4章の検証コマンド（テスト等）と、14章のCodex起動コマンド。1回の実行ごとに、WP記録7.2節に1行記録する。
- 記録する項目と取得方法：

| 項目 | 取得方法 | 取得できない場合 |
|---|---|---|
| 実行日時 | 実行の直前に `date` を単独で実行した出力 | 「未取得」と記録する |
| 実行時ディレクトリ | 実行の直前に `pwd` を単独で実行した出力 | 「未取得」と記録する |
| 実コマンド | 実際にツールへ渡したコマンド文字列そのまま（WP記録の記載と一致することも確認する） | — |
| 終了コード | 次のどちらかで実測できた値だけ。(a) コマンド自身に終了コードを出力させる形（例：`<コマンド>; echo "EXIT_CODE=$?"`）をWP記録で承認済みの場合の、その出力。(b) ツールが終了コードを明示的に表示した場合（例：`Exit code 1`）の、その表示 | 「未取得」と記録する |
| 結果 | 出力の要点と、期待結果に対する判定（PASS / FAIL / 判定保留） | — |

- **終了コードを推定しない**：ツールに終了コードの表示がないこと、エラー表示がないこと、出力の内容（`OK` 等）から、終了コードを0と推定しない。
- 期待結果に終了コードを含む検証で、終了コードが未取得の場合は、その検証をPASSとせず「判定保留」とし、統括はS8で停止する。
- `date`・`pwd` は直前に別の単独コマンドとして実行するため、記録される値は「直前に取得した値」である。7.2節にはその取得方法を併記する。
- 検証担当はWP記録4章に列挙されたコマンドしか実行しないため、検証担当が実行する `date`・`pwd`・(a)の形は、4章に列挙して承認を受ける。(a)は `;` を含む複合コマンドであり、WP-P1の4.2節（チェックポイント用コマンドを `;` でつながない）とは別の形である。採用するかはWP記録のDRAFTで決める。
- `date`・`pwd`・(a)の形がHuman Gate hookでAllowされるかは未確認である（13章）。Blockされた場合はS1で停止する。

## 9. Human Gateとの関係
- **WP承認は、Human Gate hookのBlock解除を意味しない。** Blockされた操作を行うかは、人間が判断し、人間が実施する。
- WP承認は、commit / push / tag / deploy の承認を含まない。
- Codex起動は、WP承認とは別に、WP記録0章の「Codex起動の承認」に人間の個別承認（承認文言の要旨と日時）が記録された場合だけ、14章の範囲で行える。
- Codexの `VERDICT: APPROVED` は、Human Gate（保持・commit等の判断）の代わりにならない。
- 権限確認ダイアログでの許可は、WP承認とは別の判断である。

## 12. Phase B 承認前の確認事項
- **git状態の確認方法**：Phase Aの事前確認で、`git branch --show-current`・`git rev-parse HEAD`・`git status --porcelain --untracked-files=all` をまとめた1件のコマンドがHuman GateにBlockされた（原因は未確定）。統括・検証が使うgit読み取りコマンドの形と、Blockされた場合の扱い（人間が自分のシェルで確認する等）を、Phase Bの承認前に決める。
- **tempfileの利用**：パイロットのテストが `tempfile` で一時ファイル・一時ディレクトリを作ることは、ファイル作成を伴う。作成場所（OSの一時ディレクトリ）と後片付けを確認し、WP-P1の「許可された副産物」（6.5節）に列挙するかを承認前に決める。
- **共通 `scripts/` への影響**：ルートの `scripts/` は全プロジェクト共通の運用スクリプト置き場である。パイロットのファイルを置くことの可否、他プロジェクトへの影響の有無、破棄時の扱いを、承認前に確認する。
- **Python実行時の副産物**：`__pycache__/` の生成（`.gitignore` 対象）を、WP-P1の「許可された副産物」（6.5節）に列挙するか。
- **チェックポイントの取得方法**：変更ファイル一覧と各ファイルのSHA-256を得る読み取り専用コマンドの形と、Human Gate hookの判定（6.4節）。あわせて、WP記録の1〜5章が承認時から変わっていないことの確認方法（例：承認時に1〜5章の要旨または対象範囲のハッシュを人間が記録する）。
- **Python実行環境**：使用する `python.exe` のパスと存在。
- **canonical leafの集約値の取得コマンド**：読み取り専用のコマンドの形と、Human Gate hookの判定（6.6節の対象WPでは不要）。
- **サブエージェントへのHooks・権限設定の継承**、およびリポジトリ直下で起動した場合のエージェント定義の読み込み。
- **故意のBlock試験（旧V8）は実施しない。**

  2. WP記録5.1節で「使用：する」とし、回数・実施する段階・対象（`<SCOPE>` に入れる範囲文）・起動コマンドの全文・前後比較の確認対象が承認されている（1〜5章のため、6.4節の1〜5章の確認で固定される。WP-P1ではC5）。

### 14.3 手順
1. **事前取得**：5.1節の確認対象を、統括が1件ずつ取得する。
2. **事前記録**：事前取得の値を、WP記録7.3節に追記する。以後、起動までに3・4以外の操作をしない。
3. **promptの組み立て**：Skillの `references/prompt-template.md` の固定文の `<SCOPE>` に、5.1節の範囲文を変えずに入れる。diff本文やファイル内容は入れない。
4. **起動**：直前に `date`・`pwd` を単独で実行し（6.7節）、5.1節の起動コマンドを記載どおり1回だけ実行する。
5. **事後取得**：起動コマンドの終了後、WP記録を更新する前に、1と同じ確認対象を同じコマンドで取得する。区分（14.4節）がC-BLOCKの場合は行わない。それ以外（C-WRAPPERを含む）は、停止する場合も停止の前に行う。
6. **記録と比較**：起動の実測証拠を7.2節に、区分と前後比較の結果を7.3節に追記する。
7. **次の動き**：14.4節の区分と14.5節の比較結果に従う。

- **記録更新と取得・比較のタイミングを区別する**：WP記録の更新は2と6だけで行う。1と5の間に行う記録更新は2だけであり、その変更はWP記録自身の7章に限られる（WP記録自身はハッシュ対象外。1〜5章は6.4節の方法で確認する）。5の事後取得は、6の記録更新より前に行う。比較は1と5の取得値どうしで行い、その結果を6で記録する。
- 1・5の取得コマンドがBlockまたは権限拒否を受けた場合は、S1で停止する。

### 14.4 結果の区分
上から順に判定する。

| 区分 | 条件 | 状態 | 停止条件 |
|---|---|---|---|
| C-BLOCK | 起動コマンドがHuman Gate hookにBlockされた、または権限拒否を受けた（コマンドは実行されていない） | `STOPPED` | S1 |
| C-WRAPPER | wrapper異常。出力先頭の `WRAPPER_STATUS` が `OK` 以外（`CAPABILITY_FAILED` / `INVOCATION_FAILED` / `CONTRACT_INVALID` / `USAGE_ERROR`）、`WRAPPER_STATUS` 行が得られない（ツールのタイムアウト等を含む）、または実測した終了コードが `WRAPPER_STATUS` と対応しない（OK=0、CAPABILITY_FAILED=1、INVOCATION_FAILED=2、CONTRACT_INVALID=3、USAGE_ERROR=64） | `STOPPED` | S8 |
| C-NOT-APPROVED | `WRAPPER_STATUS: OK` かつ `VERDICT: NOT APPROVED` | `STOPPED` | S9 |
| C-APPROVED | `WRAPPER_STATUS: OK` かつ `VERDICT: APPROVED` | 14.5節の比較と完了判定へ進む | — |

- C-WRAPPERは、Skillの手順4に従い失敗（NOT APPROVED相当）として扱う。`REASON` をそのまま記録・報告し、再試行や別経路への切り替えはしない。結果を「概ね問題なし」等と解釈しない。
- C-NOT-APPROVED・C-APPROVEDでは、Skillの手順5に従い、7フィールド（VERDICT / BLOCKING / MAJOR / MINOR / SUGGESTIONS / EVIDENCE / REVIEWED_SCOPE）を要約・省略せずに人間へ提示する。BLOCKING・MAJORがあっても、自動で修正を始めない。
- 終了コードが未取得の場合は「未取得」と記録し（6.7節）、`WRAPPER_STATUS` から推定しない。区分は `WRAPPER_STATUS` で判定する（Skillの手順4）。
- C-APPROVEDは、Human Gate（保持・commit等の判断）の代わりにならない。
- どの区分でも、同じ起動を再実行しない。

### 14.5 Codex前後の比較
- 比較は、**5.1節の確認対象（例：ブランチ、HEAD、作業ツリーの変更ファイル一覧、各ファイルのSHA-256、1〜5章の確認値（6.4節。WP-P1ではC5））についての差分検査**である。確認対象に差分がなくても、「Codexが一切書き込みをしなかった」とは記録・報告しない。記録は「確認対象に差分なし」とする。
- 比較で検査できない場所の例：`.gitignore` の対象（作業ツリーの一覧に表れない）、リポジトリ外（OSの一時ディレクトリ、`~/.codex/`、canonical leaf（6.6節）等）、WP記録自身（ハッシュ対象外。1〜5章は6.4節の確認、6〜10章は追記のみであることで確認する）。
- wrapper経由で起動されたCodexが、自らの動作のために `~/.codex/` 等を使うことは、統括の直接操作ではなく、本比較では検査できない。これを理由に、統括・サブエージェントによる `~/.codex/` の読み書きを許可するものではない（WPテンプレート3章の禁止範囲を維持する）。
- 確認対象に差分があった場合は、区分にかかわらずS2またはS3で停止し、`READY_FOR_GATE` にしない。差分を戻すかは人間が判断する。
